# Kamatera PostgreSQL

This Compose project runs PostgreSQL 16 and a small API in dedicated containers. PostgreSQL uses a named persistent volume and is bound only to `127.0.0.1:55432`; it is not publicly reachable. The API joins the `cavalry-books-private` Docker network, syncs the catalogue from Apps Script every five minutes, and serves the most recently successful snapshot at `/api/v1/catalog`. It also provides session-protected admin reads for documents, receipts, payment SMS, reminders, customers, and expenses. Admin list data is cached for up to two minutes (payment SMS for 15 seconds; reminders for 30 seconds), and successful admin writes through the app invalidate the cache. Public order-status reads use a 30-second cache keyed by a SHA-256 hash of the unguessable tracking token; successful admin writes invalidate this cache too. The API binds to `127.0.0.1:3100` on the VPS for Nginx reverse proxying.

The database has a 384 MiB memory limit and a 0.5 CPU limit; the API has a 192 MiB memory limit and a 0.5 CPU limit. Failed or empty catalogue syncs leave the last-known snapshot intact. Google Sheets remains the source of truth: the API verifies each staff session against Apps Script and refreshes an expired read cache from Apps Script on demand. Invoice, payment, document, production, reminder, and expense writes continue to use Apps Script; the API never records a receipt. Public order-status links are read-only bearer links; the customer page omits phone numbers and payment references. The frontend falls back to Apps Script if the API is unavailable.

The deployment generates `/opt/cavalry-bookshop-db/.env` on the server with restrictive permissions. Do not copy the password into source control, frontend JavaScript, or public documentation.

The admin portal is hosted at `https://api.cavalrypublishers.co.ke/admin/`; it skips loading the public catalogue and uses the existing Apps Script staff login. The API stores only a SHA-256 hash of registered staff session tokens. Cached admin data is returned only to an active registered session. Admin writes still go directly to Apps Script and invalidate the VPS cache after success.

Staff can archive and restore orders, void and restore receipts, and archive or permanently delete unlinked payment SMS records. Voided receipts remain in the audit history and are excluded from invoice balances and revenue totals. Orders linked to invoices, receipts, or deliveries cannot be permanently deleted; archiving disables their public tracking link while retaining the record. Archive/void metadata is stored in additional columns on the relevant Sheets tabs. Catalogue books can be permanently removed from the `books` sheet; saved invoice and order item snapshots remain unchanged, and the VPS catalogue cache is refreshed after removal.

Each order row stores a 64-character random tracking token in column N and its expected delivery date in column O of `orders_log`. New production orders default to the third working day after production starts (Monday-Friday); staff can update the date from the Production page. The shareable link opens `/admin/order-status.html#<token>`; the token stays in the URL fragment and is sent to the API in a POST body, rather than being included in browser or proxy request paths. The page shows the order items, payment totals/status, expected delivery date, and production progress. Tracking links are sent in the accompanying WhatsApp message, not printed on the invoice. Deploy the updated `code.gs` to Apps Script as well as the VPS API for token creation, date updates, and status lookup to work.

Copy `api-backend/` beside `compose.yaml` on the VPS before running `bash deploy.sh`. Install `deployment/kamatera/nginx/api.cavalrypublishers.co.ke.conf` in `/etc/nginx/sites-available/`, enable it in `sites-enabled`, create `/var/www/cavalry-api-acme`, then run `nginx -t` and reload Nginx. The API host must already resolve to the VPS and have its Let's Encrypt certificate. Copy `index.html`, `app.js`, `styles.css`, `order-status.html`, `payment.html`, `manifest.json`, and the `favicon/` folder to `/opt/cavalry-books-admin/` for the portal's static files.

Run `bash rotate-password.sh` on the VPS to rotate the database password and recreate the containers without removing the data volume.

## Live M-Pesa Buy Goods STK

The API can create invoice-specific payment links and initiate Safaricom M-Pesa Express STK Push requests for the live Buy Goods shortcode. For this deployment, configure `MPESA_ENVIRONMENT=production`, `MPESA_SHORTCODE=7637201`, the production `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, and `MPESA_PASSKEY` in `/opt/cavalry-bookshop-db/.env`. Keep this file mode `600`; never put these values in frontend files or source control. The STK transaction type is `CustomerBuyGoodsOnline`. The callback endpoint is `https://api.cavalrypublishers.co.ke/api/v1/mpesa/callback`.

The VPS sends a receipt to Apps Script only after the STK callback matches the requested invoice, amount and phone, and a Safaricom STK Query confirms success. To authorize this server-to-server write, generate one random secret on the VPS (for example `openssl rand -hex 32`), set it as `MPESA_APPS_SCRIPT_SECRET` in the VPS `.env`, and set the exact same value as the Apps Script **Script Property** `MPESA_PAYMENT_API_SECRET`. Do not send the value in chat, add it to source files, or use a client-visible property. Deploy the updated `code.gs` as a new Apps Script version after adding the property.

The customer enters their M-Pesa phone number on `/admin/payment.html`; the amount is read from the current invoice balance at checkout and must be a whole shilling amount. New invoices round to the nearest shilling and show any adjustment as a separate line. Existing invoices with fractional balances are blocked from STK checkout until staff adjust them. Callback retries are persisted in PostgreSQL and processed idempotently; status `REVIEW_REQUIRED` means staff should reconcile the payment before recording it manually.
